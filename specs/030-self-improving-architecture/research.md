## R1 OMP memory check

- **Decision**: In `scripts/check-omp-baseline.sh`, read the `backend:` line under `memory:`. `false` and `off`, quoted or not, pass. Any other value fails with `memory enabled: backend=<value>`. A missing `memory:` block, or a missing `backend:` line, fails with `memory key missing`.
- **Rationale**: `.omp/config.yml` line 54–55 is `memory:` / `backend: false`. The current check is `grep -A1 '^memory:' | grep -qE 'backend: "?off"?'`, so it rejects `false`. That is the root cause of e-205, e-207, e-209, and e-211.
- **Test location**: `tests/test_policy_conflicts.py`, the existing home for repo-contract checker tests (`check-policy-conflicts`). No new `test_omp_baseline.py`.
- **Alternatives**: changing the config to `"off"` was rejected, because it hides a checker defect and the spec calls `false` correct (US1-1). A YAML parser in bash was rejected; one `python3 -c` with PyYAML is acceptable but not needed for one key.

## R3 errors.md format and matching

- **Decision**: store one JSON line per entry, `{"id","cause","source","evidence":[{"sitting","detail"}]}`, keeping the `# Error ledger` heading.
  - `append --source S --cause C --sitting X [--detail D]` auto-attaches only when an open entry has `source == S` and `cause.strip() == C.strip()` (FR-007, b14ea71b). It reports `{"status":"attached","id","occurrence_index"}`. With no match, it creates an entry.
  - `--source` must name an existing repo path or `external:<name>`; this is a deterministic check. `list` also reports open entries whose `source` no longer exists (`missing_sources`).
  - `--attach e-N` is the agent's same-root-cause call. It overrides only the cause match and is refused (exit 2 plus a hint, nothing written) when e-N's `source` differs. A regression test covers the refusal. The rule for making that call goes in `AGENTS.md` "Error ledger": attach when the fix for e-N would also remove this failure; otherwise create.
  - `detach --id e-N --index k` removes one occurrence. It is the one documented undo for an attach, and it refuses to remove an entry's only occurrence (use `drain`).
  - `drain --id e-N` deletes the entry. `--cause-fixed` is removed along with the `cause_fixed` field (FR-006). Passing it exits 2 with a hint and the correct example, and `AGENTS.md` line ~200 is updated in the same change.
- **Rationale**: code makes only the exact match. Deciding that differently worded causes share a root is judgment, so it belongs to the agent (FR-046 rule 5). The earlier normalized `cause_key` (casefold, digits, and literals stripped) was a heuristic judgment and is dropped.
- **Migration** (FR-010): a one-off, uncommitted conversion. No `migrate` subcommand is added and no group ids are hardcoded. This follows the same precedent as the eval corpus conversion: constitution VIII does not apply to one-offs, and FR-046 rule 1 forbids a command used once. The deterministic part: drop `status == "drained"` lines, map each open entry to `{id, cause, source, evidence:[{sitting, detail: cause}]}`, and concatenate `evidence` into the kept id for each merge group. The agent supplies the merge groups and `source` values as input data. Current proposal, from reading the causes:
  - OMP: e-205, e-207, e-209, e-211 → e-205, `source: scripts/check-omp-baseline.sh`
  - Vale: e-212, e-214, e-215, e-216, e-218 → e-212, `source: .vale.ini`
  - Identity: e-206, e-208, e-213 → e-206, `source: tools/wiki_ops/identity.py`
  - Other open entries: e-168 → `.agents/skills`, e-201 → `.agents/skills/wiki-lint/SKILL.md`, e-202 → `scripts/wiki`, e-203 → `.agents/skills/wiki-lint/SKILL.md`, e-210 → `.agents/skills/skill-creator/scripts/run-eval.py`, e-217 → `.agents/skills/wiki-lint/SKILL.md`. These are the agent's reading, and the migrating agent confirms them.

  Order, as in plan.md: the Phase 1 fixes drain the OMP, Vale, and e-210 entries first, each in the same commit as its fix (FR-008). The Phase 2 migration then converts only the entries still open, and after it `error-ledger.py` loads only the new format. Today `error drain --id e-N` requires `--cause-fixed true` (`scripts/error-ledger.py:94` returns "Drain-without-fix is invalid" otherwise). Drains made before the `--cause-fixed` rejection lands keep the flag: `python3 scripts/error-ledger.py error drain --id e-N --cause-fixed true`. After it lands, the flag exits 2.
- **Recurrence**: a field of `error list`: `{"entries":[…], "recurrence":{"total": Σ(len(evidence)-1), "by_sitting":{…}}, "missing_sources":[ids]}`. `scripts/wiki`'s two `error list` callers (lines ~201 and ~587) read `entries`.
- **Alternatives**: a separate `recurrence` subcommand was rejected (one list is enough). A committed `migrate` subcommand with hardcoded groups was rejected, because it encodes a judgment and runs once. Keeping `status`/`cause_fixed` was rejected, because only open entries remain.

## R4 Scoped identity

- **Findings from code**: `scripts/wiki lint` always calls `scripts/wiki-lint --scope files:<cache misses>`. Whole-vault lint is therefore the scoped path with every miss selected. `scan_identities` always runs `_pages(vault)`: it does `rglob`, reads every page, and builds a `Counter` of body characters for every page. Since 6c374829, only pairs touching the selected pages are compared. Measured today: identity takes 843 ms for 1 page, of which the whole-vault read and profile is the bulk. `resolve_identity` (mutation gate) and `_path_for` also walk the vault.
- **Decision**: keep a derived index, `wiki/_meta/identity-index.json` (data-model §4), loaded and saved by `tools/wiki_ops/lint_cache.py` with its existing atomic writer and `sha256_file` (no new cache module). `resolve_identity` (the mutation gate) and `_path_for` use the same index, so no identity path walks the vault. The thresholds (> 0.6, > 0.7) only list candidates and set `ambiguous`; they never pick a winner, and resolution is the agent's under `wiki-dedup`/`wiki-lint` (FR-024). The index holds one row per page: the cheap fields plus a compact character profile, keyed by `content_sha256`. On each run:
  1. List paths (`os.scandir` walk; `stat` only).
  2. For each path whose `(size, mtime_ns)` differs from the row, rehash. If the hash differs, re-read that one page and rebuild its row.
  3. Drop rows for missing paths.
  4. Build exact maps from the rows: `norm(title)`, `norm(alias)`, and `stem` → paths. Load the manifest provenance and transitions.
  5. For each selected page, candidates = same `type`, no redirect, and (title/alias match, OR shared provenance with stem ratio > 0.7, OR a merge transition, OR a profile-prefilter pass > 0.6).
  6. Run `SequenceMatcher` only for candidate pairs whose `(sha_a, sha_b)` ratio is not already in the index's `pairs` map; read only those bodies.
  7. Report `compared = |selected ∪ candidates|`.
- **Rationale**: the candidate predicate is exactly the one in today's `_resolve_row_identity`, evaluated from cached data. Scoped, cached, cold, and whole-vault findings stay identical (FR-025/FR-026), and the vault is no longer re-read on every run. The index format version and the `.manifest.json` hash sit in the header. A version mismatch or parse error rebuilds the index (spec Edge Case).
- **Alternatives**: a separate identity cache module was rejected, because `lint_cache.py` already owns derived-cache I/O (FR-046 rule 1). Storing identity rows inside `lint-cache.json` `extracts` was rejected, because lint-cache entries are invalidated by the rules digest and exist only for linted pages, while identity needs every page. Dropping the content-similarity candidate path to match FR-024's literal list was rejected, because it changes findings (spec gap 1 in plan.md). A daemon or SQLite store was rejected (XIV).

## R5 Evaluator unification

- **Decision**: `scripts/luna-eval` stays the only runner. It adds three things:
  - repo-root discovery through the shared `tools/wiki_ops/cli.py` helper (replacing `git rev-parse` from the working directory), so it runs from any working directory.
  - `metrics.json`, derived after the run from `events.jsonl` (codex `--json` event stream): `tool_calls` by kind, `total_tool_calls`, `retries` (a failed command re-run with the same argv), `invocation_errors` (FR-027 command calls rejected as usage errors, counted even when corrected; data-model §3; the SC-010 measure), `duplicate_actions` (an identical command or file edit repeated after success), `tokens` (the sum of `turn.completed.usage`), `completion_reason` (exit/usage-limit/no-output code), `model` and `effort` as passed to codex (FR-019), and `skills_read` (`SKILL.md` paths the subject opened).
  - a deterministic `skill_selected` grade in `grading.json`.

  `skill-creator` then invokes `luna-eval` per eval and config. `run-eval.py`, `run-loop.py`, `improve-description.py`, and `generate-report.py` (which only renders `run-loop.py` output) are deleted along with the "Description optimization" section of `SKILL.md`.
- **Schema check**: in `luna-eval`'s `load_eval`, which validates the whole `evals.json` against data-model §2 and exits 2 listing bad records before any subject run. `quick-validate.py` was considered and rejected: it validates `SKILL.md` frontmatter for `package-skill.py`, and FR-046 names `luna-eval` the owner of skill evaluation. Tests go in the new `tests/test_luna_eval.py` (no luna-eval test file exists). Those tests load the script with `importlib`, as `scripts/wiki` already does for `wiki-maintain`.
- **Promotion is reported, not decided**: `aggregate-benchmark.py` adds per-eval regressions (worse `task_outcome`; incumbent-pass → candidate-fail assertions) and medians of `total_tool_calls`, `retries`, `tokens.total`, and latency. It prints no verdict. The keep/refuse rule is text in `skill-creator/SKILL.md` (FR-044). Skill selection is proven by `skill_selected` records in the same `evals.json` (FR-015).
- **Rationale**: e-210 is the second-runner defect. The viewer and `aggregate-benchmark.py` already read `grading.json` + `timing.json` + `metrics.json`, so extending the luna-eval run directory with those files is the one shared format (spec Assumptions).
- **To verify during implementation**: the codex `--json` event names (`item.completed` with `command_execution`/`file_change`, `turn.completed.usage`) against a real `events.jsonl` from one `luna-eval` run. If they differ, `metrics.json` maps whatever is present and records `null`, never a guess.
- **Alternatives**: keeping `run-eval.py` for description triggering was rejected by FR-015. A new grader script for all types was rejected; semantic grading stays with `agents/grader.md`.
